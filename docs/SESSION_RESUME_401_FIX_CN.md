# 旧任务恢复 401 修复

日期：2026-09-05；目标版本：0.5.46。

## 已确认的根因

- 用户旧任务保留 `openai`，当前配置为 `opencodex`，实际请求错误地到达 OpenAI 官方接口，第三方凭据返回 401。
- OpenCodex 默认历史迁移与 Manager 的自定义供应商策略相冲突。
- 真实 Codex 0.153.4 隔离测试证明：仅修改 SQLite，首次恢复成功，第二次重启又从 JSONL 元数据恢复旧供应商。
- 内置 `openai` 不允许被同名自定义供应商覆盖，不能通过兼容别名解决。

## 修复边界

由 Manager 统一管理会话路由，关闭 OpenCodex 历史重映射。修复索引和会话 `session_meta` 中的供应商信息及 `thread_settings_applied` 中的供应商/模型快照；用户消息、助手消息、工具内容逐字节保留。

元数据长度变化时同步修正历史缓存中的字节位置，不删除历史缓存或会话。修改前备份，保存可重试的修复日志。只在 Codex 关闭时修改会话文件；运行中更新标记待修复，在安全启动入口处理。

覆盖更新迁移、供应商切换、同步、退出后重新登录、重复重启。未知第三方供应商不自动接管。

## 验收

- 使用临时 CODEX_HOME 和本机模拟 Responses 接口，不访问用户上游，不重启当前 Codex。
- 旧任务连续恢复并发送消息至少两轮；验证请求端点和供应商一致。
- 覆盖缓存字节偏移、备份、重复执行、失败恢复、未知供应商及会话正文不变。
- 通过跨平台检查并发布新版本，回读更新清单、签名和下载产物。

风险：已载入内存的旧任务仍需在安全时机重启 Codex 才能加载修复；不在当前对话中强制重启。

## 验证期间发现的隔离问题

原有 `report_for_path` 会调用全局 OpenCodex 状态，导致完整单元测试进入真实用户配置。旧版安装路径检测未挡住该路径，388 份历史元数据被处理。已停止该测试；逐字节核对确认这 388 份历史的全部消息内容与备份一致，当前任务和用户报告的故障任务均未被改写，原始备份保留。

已移除配置报告对全局运行状态的隐式调用；增加原生 `codex` / `codex.exe` 进程检测，检测失败视为仍在运行。后续完整测试将 HOME、CODEX_HOME、Manager 数据目录同时隔离。构建缓存空间不足通过 Cargo 清理可重建工件解决，修复流程增加磁盘余量检查。

## 最终隔离续聊验证

真实 Codex 0.153.4 加载故障任务只读克隆，完成多模型 → 默认配置 → 多模型六次冷启动恢复，每次发送消息均完成，请求端点与当前供应商一致。测试替换模拟凭据，不访问真实上游。原始故障任务 JSONL 前后 SHA-256 一致。

仅修改 session_meta 仍不足：真实克隆中的 thread_settings_applied 会在第二次冷启动重新覆盖供应商。最终实现同步这两类元数据，保留权限、工作目录及所有消息/工具行。

本地质量门：Rust 239 项通过、1 项隔离专用测试默认忽略（已单独运行）；发布测试 64 项、TypeScript、应用源码 lint 通过。前端 369 项和生产构建通过。本包 Clippy 通过；macOS 上 Windows 依赖有既有警告，跨平台严格门以 CI 为准。全量 lint 仅被本地未跟踪的压缩课件 motion.min.js 阻断，没有改动课件。六次恢复均确认 HTTP Authorization 使用当次模拟登录凭据；未替代真实 OAuth 浏览器授权验收。
