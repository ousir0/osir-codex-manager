# OSIRAPI 统一鉴权与 OpenCodex 多模型方案

## 结论

OpenCodex 作为唯一的多模型运行内核，不再开发轻量本地路由。产品只保留两条清晰路径：

1. 单供应商直连：直接配置 Codex，不安装 OpenCodex。
2. OpenCodex 多模型：完整使用 OpenCodex 的模型选择器、路由持久化和本地服务。

OSIRAPI 浏览器鉴权上移为统一账户连接层，同时服务这两种模式。

## 产品决策

- Manager 不自行实现多模型路由、协议转换或模型选择器。
- 用户启用多模型时，Manager 安装并托管经过验证的 OpenCodex 固定版本。
- OpenCodex 负责模型选择器、Provider 路由、路由锁定、模型目录和持续运行。
- Manager 负责 OSIRAPI 鉴权、安装升级、配置同步、健康检查、自动恢复、备份与回滚。
- OpenCodex 的存在需要在页面中明确展示，但安装和环境处理必须由 Manager 自动完成。

## 为什么取消轻量路由

轻量路由仍然需要处理本地端口、后台进程、模型目录、Provider 路由、协议转换、自动启动、健康检查和跨平台兼容，但能力弱于 OpenCodex。

这会形成第二套路由内核，带来重复维护和新的稳定性风险，产品价值不足。

## 统一鉴权层

OSIRAPI OAuth 只负责用户身份、订阅套餐、用量和余额、专用 Key 自动创建或复用、授权失效和重新连接状态。

OAuth 完成后，根据用户选择返回不同配置目标：single_provider 或 opencodex。

## 单供应商直连

适合只使用一个模型来源的用户。

流程：浏览器登录 OSIRAPI，服务端检查订阅和模型权限，自动创建或复用单供应商专用 Key，返回加密 Provider 配置，Manager 写入 Codex config.toml 和 auth.json。不安装、不启动 OpenCodex。

优点是安装成本最低、故障面最小，适合只需要单一模型入口的用户。

## OpenCodex 多模型

用户明确需要在 Codex 选择 GPT、Claude、Grok 等多个模型时，直接使用完整 OpenCodex。

保留 OpenCodex 的原因：能稳定生成 Codex 模型选择器目录，支持多 Provider 和 provider/model 路由，能够持久化默认模型和路由，支持本地持续运行、路由锁定、可用性验证和本地控制台。

Manager 不重写 OpenCodex，而是负责把它封装成可靠组件：下载固定且验证过的版本，使用 Manager 管理的运行时，不依赖用户全局 Node/npm，在用户目录安装，自动启动和恢复，检查 health、ready、端口和模型目录，配置前备份并在失败时回滚。

## 两种模式对比

| 模式 | 安装成本 | 适用用户 | 能力 |
| --- | --- | --- | --- |
| 单供应商直连 | 最低 | 只使用一个模型来源 | 单 Provider、单 Key、当前模型 |
| OpenCodex 多模型 | 较高但能力完整 | 需要多模型选择器 | 多 Provider、模型目录、持久路由、控制台 |

## 产品入口

页面提供“单供应商直连”和“OpenCodex 多模型”两个明确入口。选择单模型时直接配置 Codex；选择多模型时，Manager 自动完成 OpenCodex 的安装、运行环境准备、配置和验证，用户不需要手动安装 Node/npm 或执行命令。

多模型状态卡需要持续显示：OpenCodex 版本、运行状态、模型数量、当前默认路由、路由可用性和最近同步时间。异常时提供一键修复、重启服务和恢复上次可用配置。

## 推荐开发顺序

### P1：统一 OSIRAPI 鉴权

把账户连接与 OpenCodex 配置拆开，OAuth 返回统一用户、订阅、用量和 Key 状态。

### P2：单供应商 OAuth

增加 single_provider 配置交付，直接写入 Codex。

### P3：强化 OpenCodex 组件管理

完善固定版本、受控运行时、开机恢复、健康检查、崩溃恢复和回滚。

### P4：统一配置工作台

页面只展示单供应商和多模型两种当前生效模式，避免两套配置同时编辑。

## 最终判断

OSIRAPI 登录是共用的账户连接能力；OpenCodex 是唯一的多模型完整实现，不再增加轻量中间层。

最终路径：OSIRAPI 登录一次，单供应商直接使用；或选择多模型后由 Manager 安装并持续管理 OpenCodex。

## 反思

这里解决的是多模型运行稳定性的根因，而不只是减少安装体积。最大的实现假设是 OpenCodex 的固定版本接口和模型目录格式可被持续兼容，因此 Manager 必须做版本锁定、升级前验证和失败回滚。
