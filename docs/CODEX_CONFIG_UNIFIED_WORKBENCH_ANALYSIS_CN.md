# Codex 配置管理统一工作台分析与整合方案

## 结论

基础配置和多模型配置不是同一个功能，但现在都在修改 Codex 的当前模型、供应商、Base URL 和生效路径，因此用户会感觉重复，甚至担心互相覆盖。

推荐统一成：

> 一个 Codex 配置工作台 + 两种连接模式 + 一套共享的安全与恢复能力。

两种连接模式：

- 单供应商模式：一个 Provider、一个 Base URL、一组凭据、一个当前模型。
- 多模型模式：OpenCodex 本机路由、多个供应商、多个模型、OSIRAPI 订阅连接。

MCP、图片生成、权限策略和高级 TOML 不属于连接模式，应作为共享模块独立管理。

## 当前冲突

### 1. 两套页面都在配置模型

基础页面负责 Model、Provider、Base URL、API Key、模型获取和运行参数；多模型页面负责 OSIRAPI、路由、默认模型、OpenCodex、模型目录和路由验证。

用户看到的是两个都能配置模型的入口，但 Codex 实际只有一个生效配置。

### 2. 两套凭据容易混淆

基础模式使用 Codex 的 auth.json；多模型模式使用 OpenCodex 私有配置中的多条 Key。多模型启用后，如果基础页面仍显示普通 API Key 编辑器，用户可能重复填写，甚至覆盖代理配置。

### 3. 默认模型含义不同

基础模式的默认模型是 Codex 直接请求的模型；多模型模式的默认模型是 provider/model 路由。页面应统一使用：

- 单供应商：当前模型
- 多模型：当前默认路由

### 4. 保存逻辑有覆盖风险

基础保存修改 config.toml 和 auth.json；多模型保存修改 OpenCodex 配置、模型目录和 Codex 本地 Provider。两者同时可编辑时，最后一次保存可能导致选择器为空、OpenCodex 被覆盖或 auth.json 与实际调用路径不一致。

## 推荐信息架构

不建议继续把“基础”和“多模型”作为两个平级 Tab。建议改成四个模块：

1. 连接模式
2. Codex 行为
3. MCP 与工具
4. 高级与恢复

“连接模式”是主模块；其他模块对两种模式共享。

### 连接模式卡片

页面顶部显示两个模式卡片：

| 模式 | 适用场景 | 主要配置 | OpenCodex |
| --- | --- | --- | --- |
| 单供应商 | 只连接一个 API 服务 | Provider、Base URL、API Key、当前模型 | 不使用 |
| 多模型 | 在 Codex 中选择 GPT、Claude、Grok 等模型 | OSIRAPI、路由、模型目录 | 使用 |

每张卡必须显示“当前使用中、可切换、未配置或连接异常”，不要让用户自己猜当前模式。

### 唯一生效状态

Manager 应统一计算 effectiveMode：

- none：没有可用连接
- singleReady：单供应商可用
- multiReady：多模型和 OpenCodex 可用
- multiError：多模型已配置但服务或目录异常
- signedOut：历史连接存在但账号已退出或授权失效

顶部只展示一个“当前生效模式”，基础和多模型页面都读取同一份状态。

## 推荐页面布局

### 顶部状态栏

显示当前生效模式、调用路径、配置文件状态、OpenCodex ready、模型数量和备份状态。

## 基础模式如何简化

基础模式不应让用户直接理解完整 TOML。建议改成三步：

1. 选择供应商：OSIRAPI、OpenAI Compatible 或自定义供应商。
2. 连接凭据：Base URL、API Key、凭据状态。
3. 选择模型：获取模型、手动输入、标记当前模型。

保存后只给结果提示：

> 单供应商已连接 · gpt-5.6-sol · 重启 Codex 后生效

推理等级、Personality、Goal Mode、审批策略和沙箱模式移到“Codex 行为”。MCP、图片生成和原始 TOML 不再堆在基础表单里。

## 多模型模式如何定位

多模型不是另一个基础配置表单，而是“连接并管理多个模型来源”的工作区。主线固定为：

`连接账户 → 检查权益 → 导入路由 → 同步模型 → 验证或锁定路由`

多模型页面只关注 OSIRAPI 连接状态、用户与套餐摘要、路由状态、模型数量、默认路由、OpenCodex ready，以及重新连接、同步和退出。

不要在多模型主页面再次显示普通 Base URL、auth.json API Key 和单供应商保存表单。

## 互斥规则

### 多模型已启用

基础连接字段只读：Provider、Base URL、普通 API Key、基础模型。提示：

> 当前由 OpenCodex 多模型接管。若要配置单一供应商，请先切换到单供应商模式。

Codex 行为、MCP、图片生成和高级恢复仍可编辑。

### 单供应商已启用

多模型模块显示“未启用”或“可启用”，不把路由列表伪装成当前生效模型。

### 模式切换必须是事务

1. 备份 config.toml、auth.json、OpenCodex 配置和模型目录。
2. 展示切换影响。
3. 写入目标模式。
4. 校验目标模式和健康状态。
5. 更新当前模式。
6. 失败时自动恢复原模式。

## 共享模块

### Codex 行为

- 推理等级
- Personality
- Goal Mode
- 禁用响应存储
- 审批策略
- 沙箱模式

### MCP 与工具

继续管理 MCP 列表、启用/停用、添加、编辑和敏感字段提示。图片生成 API 作为独立工具能力管理，不放进供应商连接表单。

### 高级与恢复

只放原始 TOML、配置校验、模型目录路径、OpenCodex 端口、备份恢复、诊断和受管字段说明。

## 实施顺序

### P1：统一状态

增加 effectiveMode、connectionStatus、activeModel、activeRoute 和 configOwner。基础页面和多模型页面都读取同一份状态。

### P2：重排页面

把平级 Tab 改为“连接模式 + 共享模块”；基础模式改为三步表单；多模型保留路由工作区。

### P3：互斥写入

多模型接管时锁定基础连接字段；单供应商保存时禁止覆盖 OpenCodex 受管字段；模式切换统一备份、校验和回滚。

### P4：状态和用量

显示 OSIRAPI 用户、套餐、余额和用量；增加连接异常、退出、重新连接和重新同步。

### P5：验收

验证单供应商不会破坏多模型，多模型不会覆盖 auth.json，模式切换可恢复，Codex 选择器能显示真实模型，用户始终能看懂当前调用路径。

## 最终建议

不要删除基础功能，也不要把多模型塞进基础表单。应把“连接方式”提升为一级概念：

- 基础配置负责“一个供应商能不能用”；
- 多模型配置负责“多个模型来源如何统一使用”；
- Codex 行为、MCP、图片生成和恢复负责“使用方式如何控制”。

这样既保留单供应商用户的简单路径，也让多模型用户不会被普通 API Key 和 Base URL 干扰。

## 反思

真正需要解决的根因不是页面美化，而是缺少唯一的“当前生效模式”。模式状态统一后，按钮、字段、错误提示和页面层级都会自然清晰。
