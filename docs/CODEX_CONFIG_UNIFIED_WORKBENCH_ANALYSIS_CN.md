# Codex 配置管理统一工作台分析与整合方案

> 状态：交互与布局方案草案，待确认后统一实施
>
> 更新日期：2026-08-20

## 结论

基础配置和多模型配置不是同一个功能，但现在都在修改 Codex 的当前模型、供应商、Base URL 和生效路径，因此用户会感觉重复，甚至担心互相覆盖。

推荐统一成：

> 一个 Codex 配置工作台 + 两种连接模式 + 一套共享的安全与恢复能力。

两种连接模式：

- 单供应商模式：一个 Provider、一个 Base URL、一组凭据、一个当前模型。
- 多模型模式：OpenCodex 本机路由、多个供应商、多个模型、OSIRAPI 订阅连接。

MCP、图片生成、权限策略和高级 TOML 不属于连接模式，应作为共享模块独立管理。

本轮页面改造采用“状态常驻、编辑弹窗化”的原则：主页面只负责说明当前配置是否可用，以及用户接下来能做什么；添加、编辑、授权、删除和高风险配置统一在弹窗中完成。

## 本轮设计目标

1. 用户进入页面后，5 秒内能看懂当前连接方式、当前模型和可用状态。
2. 主页面不再长期展开大量输入框，只展示摘要、状态和操作入口。
3. 添加、编辑和连接操作不改变页面滚动位置，统一使用弹窗承载。
4. 单供应商与 OpenCodex 多模型不能同时修改同一组 Codex 连接字段。
5. 普通用户不需要理解 config.toml、auth.json、Provider ID 和模型目录。
6. 全屏工作台与紧凑窗口共用同一套信息架构，只改变排版比例和弹窗形态。
7. 每次保存都必须明确告诉用户：改了什么、是否已经生效、是否需要重启 Codex。

## 设计原则

### 状态留在页面，编辑进入弹窗

适合常驻主页面的信息：

- 当前生效模式；
- 当前供应商或默认路由；
- 当前模型；
- 凭据是否已配置；
- OpenCodex 是否运行；
- MCP 数量和启用数量；
- 最近同步、备份和错误状态。

适合进入弹窗的操作：

- 添加或编辑供应商；
- 设置 API Key；
- 选择或获取模型；
- 修改 Codex 行为；
- 添加或编辑 MCP；
- 配置图片生成；
- 切换单供应商和多模型模式；
- 退出 OSIRAPI、删除凭据、删除模型和恢复备份。

### 一个弹窗只解决一个任务

弹窗不能变成缩小后的长页面。一个弹窗最多完成一个明确目标，例如“编辑单供应商连接”或“添加 MCP”。如果步骤较多，使用弹窗内分步流程，不在同一屏堆积所有字段。

### 主操作唯一

每个弹窗只能有一个主按钮，例如“保存连接”“连接 OSIRAPI”或“添加 MCP”。取消、返回和删除使用次级按钮，避免用户无法判断下一步。

### 先校验，再切换生效

保存供应商或多模型配置时，先验证配置与运行状态；验证通过后再修改 Codex 当前生效配置。失败时保留原配置，不出现保存了一半的状态。

## 当前冲突

### 1. 两套页面都在配置模型

基础页面负责 Model、Provider、Base URL、API Key、模型获取和运行参数；多模型页面负责 OSIRAPI、路由、默认模型、OpenCodex、模型目录和路由验证。

用户看到的是两个都能配置模型的入口，但 Codex 实际只有一个生效配置。

### 2. 两套凭据容易混淆

基础模式使用 Codex 的 auth.json；多模型模式使用 OpenCodex 私有配置中的多条 Key。多模型启用后，如果基础页面仍显示普通 API Key 编辑器，用户可能重复填写，甚至覆盖代理配置。

### 3. 默认模型含义不同

基础模式的默认模型是 Codex 直接请求的模型；多模型模式的默认模型是 provider/model 路由。页面应统一使用：

- 单供应商：当前模型
- 多模型：当前默认路由

### 4. 保存逻辑有覆盖风险

基础保存修改 config.toml 和 auth.json；多模型保存修改 OpenCodex 配置、模型目录和 Codex 本地 Provider。两者同时可编辑时，最后一次保存可能导致选择器为空、OpenCodex 被覆盖或 auth.json 与实际调用路径不一致。

## 推荐信息架构

不建议继续把“基础”和“多模型”作为两个平级 Tab。建议改成四个模块：

1. 连接模式
2. Codex 行为
3. MCP 与工具
4. 高级与恢复

“连接模式”是主模块；其他模块对两种模式共享。

### 连接模式卡片

页面顶部显示两个模式卡片：

| 模式 | 适用场景 | 主要配置 | OpenCodex |
| --- | --- | --- | --- |
| 单供应商 | 只连接一个 API 服务 | Provider、Base URL、API Key、当前模型 | 不使用 |
| 多模型 | 在 Codex 中选择 GPT、Claude、Grok 等模型 | OSIRAPI、路由、模型目录 | 使用 |

每张卡必须显示“当前使用中、可切换、未配置或连接异常”，不要让用户自己猜当前模式。

### 唯一生效状态

Manager 应统一计算 effectiveMode：

- none：没有可用连接
- singleReady：单供应商可用
- multiReady：多模型和 OpenCodex 可用
- multiError：多模型已配置但服务或目录异常
- signedOut：历史连接存在但账号已退出或授权失效

顶部只展示一个“当前生效模式”，基础和多模型页面都读取同一份状态。

## 推荐页面布局

### 总体页面骨架

全屏工作台不再使用窄左侧 Tab 配合超长编辑区。推荐改成三层结构：

```text
┌─────────────────────────────────────────────────────────────┐
│ Codex 配置管理                  当前：OpenCodex 多模型  ●正常 │
│ Codex → OpenCodex → OSIRAPI        30 个模型 · 刚刚已同步     │
├─────────────────────────────────────────────────────────────┤
│ [连接与模型] [Codex 行为] [MCP 与工具] [高级与恢复]            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  当前连接卡片                         快速状态                 │
│  当前路由、模型、账号、套餐            凭据 / MCP / 备份        │
│  [管理连接] [同步模型] [检查可用性]                            │
│                                                             │
│  模型与路由列表 / 工具列表 / 状态卡                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

页面采用横向模块导航，导航下方保持完整内容画布。这样能避免全屏模式左侧再次出现一条功能导航，和应用本身的主侧栏形成“双侧栏”。

紧凑窗口使用相同模块顺序，但模块导航允许横向滚动；状态卡改为单列，弹窗从底部弹出。全屏模式弹窗居中显示，并限制最大宽度与高度。

### 页面首屏

首屏固定包含三类信息：

1. 当前生效路径：Codex 现在实际请求到哪里。
2. 可用性状态：正常、需要重启、连接异常、授权失效或未配置。
3. 主要动作：管理连接、修复、同步或开始配置。

首屏不直接出现 API Key、Base URL、沙箱模式、TOML 编辑器等输入字段。

### 顶部状态栏

显示当前生效模式、调用路径、配置文件状态、OpenCodex ready、模型数量和备份状态。

`Codex 配置管理                         [当前：多模型模式]
当前调用路径：Codex → OpenCodex → OSIRAPI 订阅路由
状态：已连接 · 30 个模型 · OpenCodex ready`

### 已连接的多模型卡片

`当前使用：多模型模式                         ● 已连接
OSIRAPI 用户：用户名 / 邮箱
订阅套餐：QA 多模型团队套餐
用量：$1,084.20 / $4,200.00
剩余：$3,115.80       有效期：24 天

[管理连接] [重新同步模型] [退出连接]`

连接成功后，不再显示主按钮“连接 OSIRAPI”，改为状态卡和管理操作。

### 单供应商卡片

`当前使用：单供应商模式                      ● 可用
供应商：OSIR
模型：gpt-5.6-sol
Base URL：api.osirclaw.com/v1
凭据：已配置

[获取模型] [保存配置]`

### 未配置状态

`选择你的连接方式

[单供应商模式]       [多模型模式]

推荐：连接 OSIRAPI 后自动导入订阅模型`

## 模块化页面设计

### 1. 连接与模型

这是默认首页，负责回答三个问题：

- 当前是单供应商还是 OpenCodex 多模型；
- 当前真正使用哪个模型或路由；
- 当前连接是否可以立即使用。

页面组成：

- 当前连接主卡片；
- 账号与套餐摘要；
- 模型或路由列表；
- OpenCodex 运行状态；
- 最近同步与需要重启提示。

主页面操作：

- 管理连接；
- 切换连接模式；
- 获取或同步模型；
- 检查可用性；
- 打开 OpenCodex 控制台。

### 2. Codex 行为

主页面以摘要卡展示，不直接展开表单：

- 推理等级；
- Personality；
- Goal Mode；
- 响应存储；
- 审批策略；
- 沙箱权限。

点击“编辑行为设置”打开弹窗。危险的 `never + danger-full-access` 组合在弹窗内实时警告，保存时再次确认。

### 3. MCP 与工具

主页面使用列表管理，每行只显示：名称、传输方式、地址摘要、启用状态和敏感字段标记。

- 点击整行：打开编辑 MCP 弹窗；
- 点击“添加 MCP”：打开新建弹窗；
- 启用开关：允许在列表直接操作；
- 删除：打开确认弹窗；
- 图片生成：作为独立工具卡，点击后打开配置弹窗。

不再在列表下方展开 MCP 编辑器，否则长列表会把编辑区推到页面底部，用户也容易忘记正在编辑哪一项。

### 4. 高级与恢复

页面默认展示诊断摘要，不直接显示大段 TOML：

- config.toml 是否可解析；
- 配置文件路径；
- 最近备份；
- Codex 是否正在运行；
- OpenCodex 端口和模型目录；
- 最近一次错误。

“编辑原始配置”打开全尺寸高级弹窗。弹窗默认遮挡敏感值；用户显式开启后才允许编辑和保存。恢复备份、重建模型目录和重置连接使用独立确认弹窗。

## 弹窗交互规范

### 弹窗类型

| 类型 | 使用场景 | 紧凑窗口 | 全屏工作台 |
| --- | --- | --- | --- |
| 编辑弹窗 | 供应商、行为、MCP、图片生成 | 底部 Sheet | 居中 Modal |
| 分步弹窗 | 新连接、模式切换、OAuth | 全屏高度 Sheet | 640–760px 宽 Modal |
| 确认弹窗 | 删除、退出、恢复、危险权限 | 小型底部 Sheet | 小型居中 Modal |
| 结果弹窗 | 授权完成、同步完成、修复完成 | 小型底部 Sheet | 小型居中 Modal |
| 高级编辑弹窗 | TOML 和诊断详情 | 接近全屏 | 大型居中 Modal |

### 统一弹窗结构

每个弹窗统一包含：

1. 顶部：任务类型、标题、关闭按钮；
2. 中部：说明、字段、即时校验和影响提示；
3. 底部：固定操作栏；
4. 主按钮：只保留一个；
5. 保存中：锁定重复提交，但允许阅读当前内容；
6. 保存成功：自动关闭普通编辑弹窗，并在主页面显示结果通知；
7. 保存失败：弹窗保持打开，错误显示在对应字段或操作区。

### 未保存修改

用户修改字段后点击关闭、遮罩或按 Esc：

- 没有修改：直接关闭；
- 有未保存修改：提示“放弃修改 / 继续编辑”；
- OAuth 等外部流程进行中：不能误关闭，必须明确取消流程。

### 字段校验

- Provider ID：只允许 Codex 可识别字符；
- Base URL：保存前检查 URL 格式；
- API Key：不回显历史值，只显示“已配置”；
- 模型：支持获取目录后选择，也允许手动输入；
- MCP 名称：检查重复；
- MCP stdio：必须有 command；
- MCP HTTP：必须有合法 URL；
- 删除当前模型：至少保留一个可用模型；
- 切换模式：必须先完成备份和目标模式验证。

## 关键操作流程

### 单供应商连接弹窗

建议采用三步流程：

1. 选择供应商：OSIRAPI、已有 Provider、自定义 Provider；
2. 配置连接：Provider ID、Base URL、API Key；
3. 选择模型：获取模型、选择当前模型、测试连接。

最后点击“保存并启用”。成功后主页面更新为：

> 单供应商已连接 · gpt-5.6-sol · 重启 Codex 后生效

已有 Provider 的“编辑”与“新建”复用同一个弹窗，但标题、默认值和保存动作不同。

### OpenCodex 多模型入口

OpenCodex 多模型保留独立工作区，因为路由、模型目录、运行状态和账号用量需要持续展示，不适合全部塞入弹窗。

弹窗只承载操作：

- 安装 OpenCodex；
- 连接 OSIRAPI；
- 手动添加供应商；
- 编辑路由；
- 移除模型；
- 切换默认路由；
- 退出连接；
- 修复或恢复。

工作区常驻展示：连接状态、账号信息、模型与路由、OpenCodex 运行状态和最近同步。

### OSIRAPI OAuth 弹窗

1. Manager 弹窗说明将打开浏览器；
2. 用户点击“浏览器登录并连接”；
3. 弹窗进入等待状态，并允许安全取消；
4. 浏览器授权成功后自动关闭；
5. Manager 回到前台；
6. Manager 校验新授权信息、账户、订阅、Key、路由和模型目录；
7. 显示结果弹窗；
8. 主页面刷新为已连接状态，不再显示“连接 OSIRAPI”主按钮。

### MCP 添加和编辑

新建和编辑使用相同弹窗：

- 第一区：名称和启用状态；
- 第二区：stdio 或 HTTP；
- 第三区：命令与参数，或服务 URL；
- 底部：敏感字段保留说明和保存按钮。

保存成功后关闭弹窗，并让更新后的 MCP 行短暂高亮，帮助用户确认修改位置。

### 图片生成工具

独立卡片展示启用状态、Base URL 和当前模型。点击“配置”后弹窗输入 Base URL、模型和新 API Key。删除 Key 使用二次确认，不能和普通保存按钮放在同一视觉层级。

### 高级配置与恢复

原始 TOML 只在高级弹窗中编辑。打开时默认只读且遮挡敏感字段；用户主动开启“显示并编辑敏感值”后才切换为可编辑。

保存前必须执行 TOML 校验。恢复备份前展示将被恢复的文件范围；恢复成功后提示是否需要重启 Codex。

## 全屏与紧凑窗口适配

### 全屏工作台

- 内容最大宽度控制在适合阅读和操作的范围，不让表单横跨整屏；
- 两列只用于“主信息 + 状态摘要”，不用于并排放置两套复杂表单；
- 模块导航保持在内容上方，不再建立第二条左侧导航；
- 编辑弹窗居中，普通宽度约 560–680px，高级编辑约 860–960px；
- 弹窗底部操作栏固定，内容区独立滚动。

### 紧凑窗口

- 所有卡片单列排列；
- 模块导航横向滚动；
- 弹窗使用底部 Sheet；
- 分步弹窗每屏只展示当前步骤；
- 操作按钮在窄屏下允许整行排列；
- 重要状态和主按钮始终优先显示。

## 状态与反馈设计

统一状态颜色和文案：

| 状态 | 页面表现 | 用户动作 |
| --- | --- | --- |
| 正常 | 绿色状态点 + 可直接使用 | 管理或检查 |
| 需要重启 | 黄色提示 + 明确说明原因 | 重启 Codex |
| 未配置 | 中性空状态 | 开始配置 |
| 授权失效 | 黄色或红色状态 | 重新登录 |
| OpenCodex 停止 | 红色状态 + 原因 | 一键启动或修复 |
| 配置错误 | 红色状态 + 保留旧配置说明 | 修复或恢复 |
| 正在处理 | 进度状态 + 禁止重复提交 | 等待或取消 |

结果提示不能只写“保存成功”，应说明影响，例如：

- “连接已保存，Codex 重启后切换到 gpt-5.6-sol”；
- “模型目录已同步，共 30 个模型”；
- “授权已失效，本地历史配置未删除”；
- “修复失败，已恢复到上次可用配置”。

## 配置安全与冲突处理

### 配置所有权

Manager 需要标记当前字段由谁管理：

- `manager_single`：单供应商配置；
- `manager_opencodex`：OpenCodex 多模型配置；
- `external`：用户或其他工具修改；
- `unknown`：无法确定。

当检测到外部修改时，不直接覆盖，先提示用户重新读取、保留外部修改或由 Manager 接管。

### 保存事务

所有会改变生效路径的操作统一执行：

`读取当前状态 → 创建备份 → 写入临时配置 → 校验 → 切换生效 → 健康检查 → 提交结果`

任一步失败都恢复原配置，并把恢复结果反馈给用户。

### 敏感信息

- 已保存 API Key 永不回显；
- OAuth 长期凭据不出现在 URL、通知或日志；
- 弹窗关闭后清空尚未保存的 Key 输入；
- 错误文案不包含完整 Token 或 Key；
- 高级 TOML 默认使用脱敏内容。

## 前端实施边界

本轮优先重构表现层和交互层，不改变已经验证通过的底层保存接口。

建议新增或抽取：

- `ConfigOverview`：当前生效状态总览；
- `ConfigModuleNav`：模块导航；
- `ConfigCard`：统一摘要卡；
- `ConfigModal`：配置编辑弹窗骨架；
- `SingleProviderDialog`：单供应商连接；
- `CodexBehaviorDialog`：行为与权限；
- `ApiCredentialDialog`：API Key；
- `ImageGenerationDialog`：图片生成工具；
- `McpServerDialog`：MCP 添加与编辑；

首轮不重写 OpenCodex 后端、OAuth 后端和 Codex 配置读写逻辑，只调整调用入口、弹窗状态和成功失败反馈。

## 基础模式如何简化

基础模式不应让用户直接理解完整 TOML。建议改成三步：

1. 选择供应商：OSIRAPI、OpenAI Compatible 或自定义供应商。
2. 连接凭据：Base URL、API Key、凭据状态。
3. 选择模型：获取模型、手动输入、标记当前模型。

保存后只给结果提示：

> 单供应商已连接 · gpt-5.6-sol · 重启 Codex 后生效

推理等级、Personality、Goal Mode、审批策略和沙箱模式移到“Codex 行为”。MCP、图片生成和原始 TOML 不再堆在基础表单里。

## 多模型模式如何定位

多模型不是另一个基础配置表单，而是“连接并管理多个模型来源”的工作区。主线固定为：

`连接账户 → 检查权益 → 导入路由 → 同步模型 → 验证或锁定路由`

多模型页面只关注 OSIRAPI 连接状态、用户与套餐摘要、路由状态、模型数量、默认路由、OpenCodex ready，以及重新连接、同步和退出。

不要在多模型主页面再次显示普通 Base URL、auth.json API Key 和单供应商保存表单。

## 互斥规则

### 多模型已启用

基础连接字段只读：Provider、Base URL、普通 API Key、基础模型。提示：

> 当前由 OpenCodex 多模型接管。若要配置单一供应商，请先切换到单供应商模式。

Codex 行为、MCP、图片生成和高级恢复仍可编辑。

### 单供应商已启用

多模型模块显示“未启用”或“可启用”，不把路由列表伪装成当前生效模型。

### 模式切换必须是事务

1. 备份 config.toml、auth.json、OpenCodex 配置和模型目录。
2. 展示切换影响。
3. 写入目标模式。
4. 校验目标模式和健康状态。
5. 更新当前模式。
6. 失败时自动恢复原模式。

- 推理等级
- Personality

- 禁用响应存储
- 审批策略
- 沙箱模式

### MCP 与工具

### 高级与恢复

只放原始 TOML、配置校验、模型目录路径、OpenCodex 端口、备份恢复、诊断和受管字段说明。

## 实施顺序

### P0：冻结交互规则

先确认模块划分、弹窗清单、全屏与紧凑布局、模式互斥和保存反馈。本阶段不改底层接口，避免界面开发过程中反复调整范围。

### P1：建立统一页面骨架

实现顶部生效状态、横向模块导航、摘要卡和通用配置弹窗。先完成响应式布局、焦点管理、Esc 关闭和未保存修改保护。

### P2：改造单供应商与行为设置

把 Provider、Base URL、模型和凭据改为分步连接弹窗；把推理、Personality、Goal Mode、审批和沙箱改为行为设置弹窗。保留现有后端保存接口。

### P3：改造 MCP、图片生成与高级配置

MCP 新建和编辑全部弹窗化；图片生成改为独立工具卡和配置弹窗；原始 TOML 改为大型高级弹窗，删除和恢复统一使用确认弹窗。

### P4：统一 OpenCodex 多模型体验

保留多模型状态与路由工作区，将安装、OAuth、添加供应商、编辑路由、删除模型、退出和修复统一为弹窗流程。已连接时只显示账号状态和管理操作。

### P5：统一状态与配置所有权

增加 `effectiveMode`、`connectionStatus`、`activeModel`、`activeRoute` 和 `configOwner`。单供应商与多模型页面都读取同一份状态，并识别外部配置修改。

### P6：互斥写入与事务切换

多模型接管时禁止单供应商覆盖受管字段；单供应商启用前停用 OpenCodex 接管。模式切换统一执行备份、临时写入、校验、健康检查和失败回滚。

### P7：联调与验收

完成前端测试、Rust 配置测试、紧凑窗口和全屏工作台视觉验收，以及真实 Codex 单供应商与 OpenCodex 多模型切换验证。

## 验收标准

### 产品可理解性

- 首屏能直接看见当前模式、当前模型、调用路径和可用状态；
- 已连接后不再出现误导性的“连接”主按钮；
- 普通操作不要求用户编辑 TOML；
- 单供应商和多模型不会同时显示为当前生效；
- 每个模块只有一个清晰主操作。

### 交互完整性

- 所有添加和编辑操作都在弹窗中完成；
- MCP 编辑不会在列表底部展开；
- 弹窗保存失败时保留用户输入；
- 有未保存内容时不能无提示关闭；
- 保存成功后主页面状态立即更新；
- 删除、退出、恢复和危险权限有二次确认；
- 键盘可完成打开、编辑、保存和关闭流程。

### 布局质量

- 全屏模式不出现应用侧栏与配置侧栏并列的“双侧栏”；
- 1366×768 下主操作和关键状态无需横向滚动；
- 紧凑窗口内按钮、字段和弹窗不溢出；
- 200% 文本缩放下弹窗操作栏仍可到达；
- 长模型名、长 URL 和长 MCP 命令不会破坏卡片宽度。

### 配置可靠性

- 单供应商保存不会破坏 OpenCodex 备份；
- OpenCodex 启用不会留下不存在的 `opencodex` Provider；
- API Key 和 OAuth Token 不回显、不进入日志；
- 切换失败自动恢复到原可用模式；
- Codex 运行中保存会明确提示重启后生效；
- 多模型同步后 Codex 选择器能读取真实模型目录。

### 测试范围

- 配置页面组件测试；
- 弹窗焦点、Esc、未保存修改和重复提交测试；
- 单供应商保存与模型获取测试；
- MCP 新增、编辑、开关与删除测试；
- OSIRAPI OAuth 成功、取消、失效和重连测试；
- OpenCodex 安装、启动、同步、停止和恢复测试；
- macOS 与 Windows 打包前的页面冒烟测试。

## 最终建议

不要删除基础功能，也不要把多模型塞进基础表单。应把“连接方式”提升为一级概念：

- 基础配置负责“一个供应商能不能用”；
- 多模型配置负责“多个模型来源如何统一使用”；
- Codex 行为、MCP、图片生成和恢复负责“使用方式如何控制”。

这样既保留单供应商用户的简单路径，也让多模型用户不会被普通 API Key 和 Base URL 干扰。

## 反思

真正需要解决的根因不是页面美化，而是缺少唯一的“当前生效模式”。模式状态统一后，按钮、字段、错误提示和页面层级都会自然清晰。
