# Codex 社区皮肤适配审查

## 结论

当前问题不是某一个 CSS 选择器缺失，而是主题协议边界被扩大了：社区皮肤提供的是受限 Safe CSS、颜色 token 和少量语义部件；Codex Manager 却把它当成可以覆盖整个 Codex 私有 DOM 和私有 token 的全局主题。两套模型叠加后，必然出现原生白色浮层、背景图穿透、局部文字颜色错误和不同页面视觉不一致。

## 社区规范能保证什么

- theme.json 提供背景图、颜色 token、构图焦点和主题元数据。
- theme.css 通过 data-ds-part 修改已注册的安全部件。
- 社区预览器执行的是审核后的 Safe CSS，并使用模拟工作区展示效果。
- 主题包不等于 Codex 全部页面的完整视觉替换；Codex 原生浮层、环境信息面板、设置页和未来版本新增 DOM 需要客户端适配。

这与 DreamSkin 文档的定位一致：主题包是本地客户端可恢复的视觉层，不是对 Codex 安装文件或全部私有组件的永久改写。

## 截图对应的实际根因

从当前 Codex 的 CDP DOM 读取到：

    main[data-app-shell-main-surface]  -> data-ds-part=main
    aside.app-shell-left-panel        -> data-ds-part=sidebar
    .ProseMirror                      -> data-ds-part=composer
    右侧环境信息面板                  -> 未注册 data-ds-part
    右侧环境信息面板背景              -> #ffffff
    Codex 原生 elevated/panel tokens  -> 仍是白色系统 token

所以截图里的白色面板不是社区主题没下载成功，而是它不属于社区 Safe CSS 的注册部件；底部白带则是背景图本身透过半透明主区显示出来。之前不断增加全局选择器，只会让更多原生组件进入半主题、半原生状态。

## 统一解决方案

采用“协议层 + 版本适配层 + 页面模式”的三层结构：

1. 协议层：只解析社区声明的颜色、背景、焦点和 data-ds-part，不再把任意社区 CSS 当作全局 Codex CSS。
2. 版本适配层：按 Codex 版本维护少量稳定的原生 token 映射和浮层选择器；未知版本使用保守模式，不覆盖私有变量。
3. 页面模式：首页允许背景图透出；对话页默认使用不透明主题主区，避免背景图干扰阅读；未注册原生面板统一使用主题 panel-alt，而不是继续显示白色系统面板。

验收标准固定为：

- 首页、对话页各一张截图。
- 侧栏、主区、Composer、消息、弹窗、环境信息面板六个区域必须同时通过。
- 明暗模式各测试一次。
- 主题切换、暂停、恢复后不能留下 data-ds-part、--cts-* 或原生 token 污染。
- 未知 Codex 版本不得使用激进全局覆盖。

## 本轮实现方向

本轮不再继续增加社区 CSS 选择器，而是：

- 将对话页主区改为不透明主题层，背景图只在首页/允许的页面模式下透出。
- 将 Codex 原生 panel/elevated/control/text token 作为一组版本适配变量统一写入。
- 将未注册的环境信息、菜单和浮层纳入当前 Codex 版本适配器。
- 保留旧皮肤兼容，但不要求旧主题包重新导入。
- 增加当前 Codex 版本的 DOM 快照验收，后续 Codex DOM 变化时先失败提示，而不是静默视觉错乱。

## 最大风险

如果目标是“任何 Codex 版本、任何页面、任何社区 CSS 都完全换肤”，仅靠外部 CSS 注入无法稳定实现；必须为每个 Codex 版本维护适配器，或者由 Codex 官方提供公开主题 token API。当前统一方案能保证视觉一致和可恢复，但不会承诺覆盖未知版本的私有页面。
